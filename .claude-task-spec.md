# Inactivity Timeout for Terminal MCP

## Goal

Add an `inactivity_timeout_secs` parameter to `terminal_execute` that kills a command after N seconds of *silence* (no stdout/stderr output), while separately enforcing the existing absolute timeout. This allows long-running commands that produce periodic output to run indefinitely (until the absolute cap) while still catching commands that hang silently.

## Context

The current timeout implementation uses `tokio::time::timeout` on `child.wait()`, which is an absolute wall-clock timeout. This works well for most cases, but some commands (like long-running build scripts or servers) produce periodic output and should be allowed to run as long as they're actively doing something. However, if such a command hangs silently, it should still be killable.

The solution is a two-tier timeout:
1. **Absolute timeout** (existing `timeout_secs`): hard ceiling regardless of activity
2. **Inactivity timeout** (new `inactivity_timeout_secs`): kills if no output for N seconds

## Test Specification (RED tests already exist)

The following acceptance tests are in `tests/mcp_stdio_suite.rs` and are currently failing (as expected):

### Test 1: `terminal_execute_inactivity_timeout_kills_on_silence`
- Command: `sleep 3` with `inactivity_timeout_secs: 1`
- Expected: `timed_out: true`, `exit_code: -1`, stderr contains "inactivity"
- Verifies: A silent command is killed by inactivity timeout before absolute timeout

### Test 2: `terminal_execute_inactivity_reset_by_output`
- Script: Output every 0.3s for ~1.5s total, `inactivity_timeout_secs: 1`
- Expected: `timed_out: false`, `exit_code: 0`, stdout contains "tick5"
- Verifies: Output resets the inactivity timer, allowing chatty commands to complete

### Test 3: `terminal_execute_absolute_timeout_beats_active_output`
- Command: Infinite loop outputting every 0.2s, `timeout_secs: 1`, `inactivity_timeout_secs: 10`
- Expected: `timed_out: true`, stderr does NOT contain "inactivity"
- Verifies: Absolute timeout still fires when it's the shorter limit

### Test 4: `terminal_execute_inactivity_beats_absolute_on_silence`
- Command: `sleep 5`, `timeout_secs: 10`, `inactivity_timeout_secs: 1`
- Expected: `timed_out: true`, stderr contains "inactivity"
- Verifies: Inactivity timeout wins when command falls silent before absolute timeout

## Implementation Requirements

### 1. Add `inactivity_timeout_secs` parameter

**File: `src/tools.rs`**

The tool registry already extracts the parameter (lines 160-161):
```rust
let inactivity_timeout_secs = args
    .get("inactivity_timeout_secs")
    .and_then(|v| v.as_u64());
```

But it's being passed to `execute` and `execute_script` which don't accept it yet.

**Changes needed:**

1. Update `execute` function signature in `src/operations/execute.rs` (line ~216) to accept `inactivity_timeout_secs: Option<u64>`

2. Update `execute_script` function signature in `src/operations/execute.rs` (line ~240) to accept `inactivity_timeout_secs: Option<u64>`

3. Update `execute_inner` signature to accept the new parameter

4. Wire through the parameter in `src/tools.rs` - fix the call sites that are currently passing 8 args to 7-arg functions

### 2. Implement inactivity timeout logic

**File: `src/operations/execute.rs`**

In `execute_inner`, after spawning the child and taking stdout/stderr pipes:

1. Create a shared "last activity" timestamp (use `std::sync::atomic::AtomicU64` for epoch millis, or a `tokio::sync::watch` channel)

2. Spawn a monitoring task that:
   - Periodically checks if `now - last_activity > inactivity_timeout`
   - If exceeded, terminates the process group (same as absolute timeout handling)
   
3. In the stdout/stderr reader tasks, update `last_activity` whenever a line is read

4. Use `tokio::select!` to race:
   - The normal `child.wait()` with absolute timeout
   - The inactivity timeout check
   
5. On inactivity timeout, set a new field in `ExecuteResult` (or reuse `timed_out: true` with the stderr message indicating it was an inactivity timeout)

### 3. Update `ExecuteResult` struct (if needed)

Consider adding a field to distinguish timeout types, or simply ensure the error message contains "inactivity" for the tests to detect.

### 4. Tool definition update

**File: `src/tools.rs`** around line 460 (`terminal_execute_tool` function)

Add the new parameter to the JSON schema:
```json
"inactivity_timeout_secs": {
  "type": "integer",
  "description": "Kill the command if no stdout/stderr output for this many seconds. Independent of the absolute timeout."
}
```

### 5. Edge cases

- If `inactivity_timeout_secs` is `None` or `0`, disable inactivity checking (use only absolute timeout)
- If `inactivity_timeout_secs >= timeout_secs`, the absolute timeout will fire first (this is fine)
- Ensure inactivity timeout works correctly with `detach: true` (should be ignored in detach mode)

## Security Considerations

- The inactivity timeout should NOT bypass the allowlist check
- Environment scrubbing still applies
- Process group termination (SIGTERM + SIGKILL) same as absolute timeout
